# 后台记忆维护与首字延迟

## 当前链路

1. 请求领取执行租约；MemoryAgent 读取 Redis/MySQL 近期原文、已完成摘要和长期画像。
2. 完成路由、知识检索、风险判断及回答规划。
3. 在同一个数据库事务保存准备结果、用户消息及 PROFILE/SUMMARY 任务。
4. 更新近期缓存，立即开始最终模型的 SSE 回答；不等待画像抽取或摘要模型。
5. 没有正在执行的聊天、且空闲达到 2 秒后，单个后台工作者领取任务。后台已有任务不会被新聊天强制中止。
6. 画像先提交 MySQL，再创建独立 INDEX 任务更新 Chroma；索引失败不回滚画像和聊天。

`MemoryAgent` 不再调用模型生成每轮摘要。近期原文仍保留在 `previousHistory` 中，供路由与风险规则使用；用于模型的历史可由已完成摘要和未覆盖的近期消息组成。摘要滞后时，近期原文优先。没有摘要时直接使用近期原文；检测到简单主题冲突时绕过旧摘要，不额外调用模型。

## 持久化和顺序

- `memory_tasks`：任务、来源请求、状态、尝试次数、下一次重试时间、执行者和租约；输入经过脱敏，管理接口不返回原文。
- `memory_worker_gate`：数据库单例协调后台工作者与前台活动标记。只在短事务持锁，模型/网络调用期间不持锁。
- `memory_user_state`：记录已提交画像的最大来源顺序。任务以请求接收时生成的回复 ID 排序，同一用户较旧的画像任务优先；写入时按属性及背景核对来源顺序，旧任务不能覆盖该属性的新值，但可补录独有的其他事实。时间、有效期、变化记录和旧画像兼容见 [事实变化管理](memory-facts.md)。
- `conversation_memory_summaries`：会话摘要、覆盖消息的时间/ID、摘要版本。
- `user_memory_items`：属性键和来源顺序。回答长短、语言、语气采用固定属性键，新表达更新同一个属性。
- 画像证据必须是本轮脱敏输入的非空连续原文；改写或凭空补充的证据不入库。此规则不等于对摘要含义的完全验证。
- Chroma 文档 ID 包含画像版本；召回必须与 MySQL 当前版本一致。遗留旧索引不会作为有效记忆返回；删除记忆的索引任务删除该记忆的全部版本。

失败任务最多执行 3 次，首次失败后等待 10 秒，第二次等待 20 秒。超过上限标记 FAILED，管理员可手动重新入队；旧画像任务仍受版本校验。进程中断后 RUNNING 任务在 120 秒租约到期后可被其他工作者领取；旧工作者即使返回，也不能提交已失去租约的结果。

任务键为用户消息 ID + 类型；恢复同一次回复复用已保存的准备结果，因此不重复创建任务。

## 增量摘要参数

| 参数 | 默认值 |
| --- | --- |
| `MEMORY_BACKGROUND_ENABLED` | true |
| `MEMORY_BACKGROUND_IDLE_MS` | 2000 毫秒 |
| `MEMORY_BACKGROUND_TIMEOUT_SECONDS` | 单次画像/摘要模型调用 15 秒 |
| `MEMORY_SUMMARY_MESSAGE_THRESHOLD` | 6 条待摘要消息 |
| `MEMORY_SUMMARY_CHAR_THRESHOLD` | 3000 字符；与消息数阈值为“或” |
| 保留原文 | 最新 6 条有效消息不纳入摘要；前台仍读取最多 20 条近期原文 |
| 单次摘要批量 | 最多 40 条、约 12000 字符 |
| 摘要目标/校验 | 目标 300–500 字，超过 1200 字符拒绝提交 |
| 模型输出预算 | 画像 600 token（最多 3 项，Ollama 使用 JSON Schema 约束），摘要 700 token |

阈值只统计上次摘要之后、且早于最新 6 条原文的有效消息。FAILED/中断的助手半段回答不进入摘要。更新输入为旧摘要 + 新增历史，不反复总结所有历史。未达到阈值的任务标记 SKIPPED。

## 管理与观测

- 管理后台“后台记忆维护”：最近 100 条任务，类型、状态、尝试次数、错误类型，FAILED 可手动重试。
- `GET /api/admin/memory-tasks`、`POST /api/admin/memory-tasks/{id}/retry`：仅管理员。
- 模型调用阶段 `MEMORY_BACKGROUND_PROFILE / SUMMARY / INDEX` 与原请求 ID 关联，区分前台响应成本和后台维护成本。
- 指标 `mindharbor.memory.queue.wait`、`mindharbor.memory.task.finished`、`mindharbor.memory.task.failed`、`mindharbor.memory.worker.errors`。

## 验收

`MemoryMaintenanceAcceptanceTests` 使用真实 Spring/JPA/聊天服务，模型与索引服务采用可控桩：

1. 连续对话：上一轮事实仍进入第二轮上下文，前台无摘要/画像模型调用；摘要达到阈值才更新。
2. 故障：画像模型失败进入重试，聊天仍 SUCCESS；索引失败不丢失已提交画像。
3. 顺序：偏好从详细改为简短后，旧失败任务手动重跑也不能覆盖新值。
4. 恢复：工作者替换/租约过期后任务被接管，旧持有者不能提交；客户端断线恢复不重复创建任务。

另外验证前台执行时不领取后台任务、管理员权限隔离。实际部署验证记录单独保存在本地 `data/deploy/`，不提交私人对话和数据库备份。

## 边界

- 空闲准入不是模型服务的抢占调度：后台调用已开始时，新聊天仍可能竞争同一块 GPU。15 秒后台模型超时限制等待，无法保证正在执行的模型计算立即停止。
- 画像、摘要和向量索引为最终一致；下一条消息可能先读到上一版画像，近期用户原文用于补充。
- 12000 字符是历史片段预算，不是整份提示词的 token 窗口保证；知识块、系统提示词还会占用空间。
- 旧版本无属性键的画像没有自动进行语义清洗。固定键解决本次改造后的偏好更新，其他属性仍依赖抽取模型返回稳定键。
- Chroma 旧版本索引当前依靠版本校验过滤，长期运行需要额外制定历史版本清理策略。
