# 流式回复失败、断线恢复和报告任务

## 已实现的用户行为

- 模型暂时失败：清空本次半段回答，显示重试提示，复用同一条回复和已经准备好的提示词重新生成。最多 **3 次总尝试（首次 + 2 次自动重试）**。
- 三次失败，或鉴权、配置、模型不存在等不可重试错误：显示失败和“重新生成”。点击后开启新的生成轮次，复用原来的请求、回复和 Agent 结果。
- 断网、刷新、关闭页面：服务端观察到连接取消后标记 `INTERRUPTED`，丢弃半段内容。重新打开并登录同一账号后，按原请求 ID 查询状态并恢复。浏览器只保存请求编号、会话编号和生成轮次，不保存密码或聊天原文。
- 如果完整回复已经落库，重连直接显示完整回复；如果另一个连接仍在生成，当前页面轮询等待，避免创建第二个生产者。
- 回复完成必须收到 `done` 或查到 `SUCCESS`；网络流结束本身不表示成功。
- Excel 和邮件任务在报告落库时登记；即使回答失败或浏览器关闭，已登记任务仍独立执行。邮件不再等待 Excel 成功。

## 状态及数据

`chat_messages` 新增 `reply_status`、唯一的 `request_id`、`prompt_json`、`request_input`、`attempts`、`generation`、执行归属、租约、剩余生成预算和错误字段。

```text
GENERATING → SUCCESS
     ↓异常      ↑
 RETRYING ───────┘
     ↓耗尽 / 不可重试
   FAILED ──手动重新生成──→ RETRYING（新 generation）

GENERATING / RETRYING ──连接取消──→ INTERRUPTED
INTERRUPTED ──恢复并取得执行权──→ RETRYING
```

- `SUCCESS` 才写完整助手正文并更新 Redis。失败、中断、重试状态的正文始终为空。
- 历史查询先筛选成功或旧版无状态消息，再取最近 20 条；失败占位记录不会挤占记忆窗口。
- 准备阶段的 Agent 结果、用户消息、运行轨迹、报告、任务和最终提示词在准备提交事务中关联落库；模型重试不会再次运行 Agent。
- 准备阶段中途故障现在支持逐步骤恢复：每请求一条最新上下文快照，子 Agent 成功后覆盖更新。租约到期后由后台扫描或前端重连接续未完成的步骤；已提交的结果不重复计算。默认每步 30 秒、每步至多 3 次总尝试、全轮准备预算 300 秒，详情与限制见 [Agent 检查点](agent-checkpoint-recovery.md)。
- 请求身份由服务端当前登录用户校验。数据库行锁和执行归属标识保证同一请求只能被一个连接领取，过期生产者不能覆盖新结果。
- 自动重试沿用累计次数。手动重新生成用 `generation` 做比较并更新，重复点击不会重复重置计数。
- 首次回复占位记录不含正文；成功后更新回复时间，以便历史中学生消息位于助手消息之前。

| 浏览器无网络数据超时 | 30 秒 |

| Agent 准备租约 | 180 秒 |

| 工具任务最多尝试 | 3 次，失败后等待 5 秒、10 秒 |

## 报告任务可靠性

`report_tasks` 使用 `report_id + kind + recipient` 唯一约束，状态包含 `PENDING/RUNNING/RETRYING/SUCCESS/FAILED/UNKNOWN`。与报告在同一事务登记；外部工具调用在事务外执行，结果再用短事务保存。线程池拒绝任务时数据库记录仍在，下轮轮询继续领取。

- Excel 以报告 ID 去重，写入临时文件后原子替换，避免重试追加重复行。当前本地文件锁只适用于单实例；多实例部署应使用统一文件写入服务或共享锁。
- 邮件复用同一通知记录，成功任务不再执行。
- SMTP 超时、连接重置、执行中进程崩溃等可能无法确定收件端是否已接收，标记 `UNKNOWN` 并在报告错误信息中显示，需人工核实，不盲目自动重发。普通 SMTP 无法保证严格只投递一次。
- 失败任务不会回滚已经持久化的心理报告或成功回复。

## API

- `POST /api/chat/stream`：`{sessionId, message, requestId}`。旧客户端可不传 requestId，新客户端必须提前生成并保存。
- `GET /api/chat/replies/{requestId}`：状态、完整正文、次数、轮次及是否已保存提示词。
- `POST /api/chat/replies/{requestId}/resume`：恢复已有请求。
- `POST /api/chat/replies/{requestId}/regenerate?generation=N`：显式重试失败回复，比较原轮次后更新。

## 边界

- 断网不是瞬间可感知的；依靠取消、心跳写失败、超时和租约恢复检测。
- 继续恢复是重新生成整段回答，不续接旧的半段 token。
- 如果服务进程在 Agent 准备结果提交前崩溃，尚无可复用的提示词。租约过期后标记失败并提示重新提交，不声称可以恢复没有落库的结果。
- 崩溃后无法准确知道未落库的消耗时间，按原截止时间保守处理；预算耗尽时需手动重新生成。
- 页面当前恢复最近一条请求；多标签页共享数据库执行权，不重复生成同一请求。
- MySQL 与 Redis 并非同一事务。完整答案以 MySQL 为准，Redis 仍是尽力更新的缓存；本改造保证半段回答不会写入两者。
- 当前使用既有 Hibernate `ddl-auto=update` 添加表与可空字段，保留旧消息。生产发布应将相应结构变更纳入正式数据库迁移流程。

## 验证

`ReplyRecoveryTests` 覆盖部分输出后重试、三次耗尽、不可重试错误、断线恢复、冻结提示词、重复提交、越权、并发领取、旧生产者写回、历史过滤、过期恢复、准备期间断线、报告任务事务回滚、Excel/邮件独立执行、未知邮件结果，以及 Excel 重复写入。

### 本次部署验证（2026-10-16）

- 自动化测试合计 119 项通过；新增恢复测试 16 项。
- Docker 六个服务已启动，应用健康检查为 UP，容器 JAR 与本地构建 SHA256 一致。
- 真实 Ollama 流式调用在首个 token 后主动断开：状态 INTERRUPTED、attempts=1、正文长度 0。
- 同一 requestId 恢复后：SUCCESS、attempts=2、完整正文 954 字符。
- 该测试会话数据库只有两条消息、一次 Agent 轨迹；Redis 只有用户消息和完整助手回复。
- 浏览器刷新后可读取已成功回复，页面恢复 READY，无前端错误日志。
